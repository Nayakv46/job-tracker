# Kubernetes

Kustomize manifests for Job Tracker. The same base is used locally (kind) and on EKS.

```
infra/k8s/
├── base/                 # environment-independent
│   ├── api/              # Deployment (+ migrate initContainer), Service, HPA
│   ├── web/              # Deployment, Service, HPA
│   ├── ingress.yaml      # public route to the web app only
│   └── kustomization.yaml  # labels, api-config ConfigMap
├── overlays/
│   ├── local/            # kind: namespace, PostgreSQL StatefulSet, secrets, ingress-nginx
│   └── eks/              # EKS: ECR images, secrets from Secrets Manager, ALB Ingress
└── kind/cluster.yaml     # local cluster with the ingress on http://localhost:8080
```

## Design

- **Only the web app is public.** The browser talks to Next.js, which calls the API server-side (pages) or through its `/api/graphql` route. The API Service is cluster-internal and has no Ingress route.
- **Migrations** run in an initContainer (`job-tracker-api-migrate` image, `prisma migrate deploy`) before each API pod starts, so a new version never serves traffic against an old schema. Prisma takes an advisory lock, so replicas starting at the same time are safe.
- **Probes:** API readiness uses `/health` (checks the database); liveness is a TCP check, so a database outage takes pods out of the Service instead of restarting them. The web app uses `/login` for both.
- **Security:** the namespace enforces the `restricted` Pod Security Standard. Pods run as non-root with a read-only root filesystem, no privilege escalation and all capabilities dropped; `emptyDir` volumes cover the paths that need writes (`/tmp`, `.next/cache`).
- **Config:** non-secret API settings are in the `api-config` ConfigMap; `DATABASE_URL`, `JWT_SECRET` and `REFRESH_SECRET` are in the `api-secrets` Secret. Both are generated by Kustomize with a content hash in the name, so changing a value rolls out new pods.
- **Scaling:** `resources.requests/limits` on every container and an HPA per Deployment (2–5 replicas at 70% CPU). Needs metrics-server.
- **Client IPs:** `TRUST_PROXY=1`, because the API's only client is the web pod, which forwards the `X-Forwarded-For` header set by the ingress controller. Spoofing the header from outside doesn't bypass the rate limit (checked).

## Run locally with kind

Requirements: Docker, [kind](https://kind.sigs.k8s.io/) and kubectl (`winget install Kubernetes.kind Kubernetes.kubectl`).

```bash
# 1. Cluster, ingress controller and metrics-server
kind create cluster --config infra/k8s/kind/cluster.yaml
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.15.1/deploy/static/provider/kind/deploy.yaml
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/download/v0.9.1/components.yaml
kubectl -n kube-system patch deployment metrics-server --type=json \
  -p '[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'
kubectl -n ingress-nginx wait --for=condition=ready pod -l app.kubernetes.io/component=controller --timeout=300s

# 2. Build the images and load them into the cluster
docker compose build
kind load docker-image job-tracker-api:local job-tracker-api-migrate:local job-tracker-web:local --name job-tracker

# 3. Secrets (local values, git-ignored)
cp infra/k8s/overlays/local/secrets/api.example.env infra/k8s/overlays/local/secrets/api.env
cp infra/k8s/overlays/local/secrets/postgres.example.env infra/k8s/overlays/local/secrets/postgres.env

# 4. Deploy
kubectl apply -k infra/k8s/overlays/local
kubectl -n job-tracker rollout status deployment/api
kubectl -n job-tracker rollout status deployment/web
```

Open http://localhost:8080.

**Demo data:** forward the database port and run the seed from `apps/api`:

```bash
kubectl -n job-tracker port-forward svc/postgres 5435:5432
# in another terminal
cd apps/api
DATABASE_URL="postgresql://postgres:local-only-password@localhost:5435/job_tracker?schema=public" npx prisma db seed
```

**After code changes:** rebuild, `kind load` again, then `kubectl -n job-tracker rollout restart deployment/api deployment/web` (the `local` tag doesn't change, so the Deployments need a restart).

**Clean up:** `kind delete cluster --name job-tracker`

### Troubleshooting: `kubeadm init` fails on cgroup v1

Kubernetes 1.35+ refuses to start on cgroup v1 hosts. Check with `docker info | grep -i cgroup`. Older Docker Desktop versions (WSL2 backend) use cgroup v1; updating Docker Desktop switches to cgroup v2. As a temporary workaround, add this to the node in `kind/cluster.yaml`:

```yaml
    kubeadmConfigPatches:
      - |
        kind: KubeletConfiguration
        failCgroupV1: false
```

## Deploy to EKS

The infrastructure comes from [`infra/terraform`](../terraform/README.md), which also creates the `job-tracker` namespace, the AWS Load Balancer Controller and the External Secrets Operator. The `eks` overlay differs from `local` in these ways:

- Images come from ECR, tagged with the git SHA (`kustomize edit set image`, see the Terraform README).
- `api-secrets` is created by an `ExternalSecret` from the Secrets Manager secret `job-tracker-dev/api`. There's no `secretGenerator`, so a new secret value needs `kubectl rollout restart deployment/api`.
- The Ingress uses the `alb` class: an internet-facing ALB that sends traffic straight to the web pods (`target-type: ip`). The ALB appends the client IP to `X-Forwarded-For`, so `TRUST_PROXY=1` still applies.
- There's no PostgreSQL in the cluster; `DATABASE_URL` points to RDS over TLS.

## Known limitations

- **Rate limits are per pod.** `@nestjs/throttler` keeps counters in memory, so with N API replicas a client can make up to N × the limit. A shared store (Redis) would make the limits cluster-wide.
- **ingress-nginx is retired** (last release March 2026). It's only used for the local cluster; EKS uses the AWS Load Balancer Controller. Moving the local setup to a maintained controller or the Gateway API is a follow-up.
